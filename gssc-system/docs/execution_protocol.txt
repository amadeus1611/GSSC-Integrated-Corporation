01. PURPOSE AND OPERATING PRINCIPLE
======================================================================
This protocol controls the complete path from a client request to a researched,
commercially defensible, client-safe GSSC quotation produced from the exact
attached GSSC template source.

The controlling principle is:

RESEARCH BROADLY. VERIFY CURRENTLY. PRICE INTELLIGENTLY. PROTECT GSSC.
DISCLOSE SELECTIVELY. PRESERVE THE TEMPLATE EXACTLY. NEVER INVENT.

This protocol has two linked engines:

ENGINE A — Research, costing, risk, legal and commercial positioning.
ENGINE B — Client-safe extraction and exact source-preserving conversion.

Research determines approved content. The attached authoritative template
determines the document. Research never authorizes redesign.

The permanent input layers are separate and must not be blended:

1. DOCTRINE LAYER — the current attached GSSC production kernel.
2. ASSET LAYER — the current attached authorized Base64 logo or asset payload.
3. STRUCTURE LAYER — the current attached authoritative quotation template.
4. EXECUTION LAYER — this protocol.
5. PROJECT LAYER — the current client request, research, specifications,
   drawings, quotations and supporting evidence.

The internal research dossier and the client quotation are separate outputs.
Internal economics, supplier information, legal analysis and negotiation limits
must never leak into the client-safe quotation.

02. AUTHORITY, PRECEDENCE AND CONFLICT HANDLING
======================================================================
Use the following order when sources conflict:

1. Current government-issued certificates, laws, regulations and official
   regulatory guidance verified for the current task.
2. Current executed or authoritative corporate records.
3. Current locked GSSC master files and the attached authoritative template.
4. Current GSSC production kernel.
5. The client's current written request and confirmed technical requirements.
6. Current verified market, supplier and labor evidence.
7. Clearly labeled reasoned assumptions.
8. Older profiles, drafts, summaries, prior quotations and chat recollections.

Do not silently choose a convenient value. Record the conflict, identify the
sources, apply the highest verified authority, and flag any conflict that could
materially change scope, price, legality, risk or delivery.

A filename containing FINAL does not by itself prove that a document is current,
executed, approved, notarized or authoritative. Inspect content and status.

Do not allow an older template, profile, quotation or draft to override current
GSSC identity, governance, tax status, public contacts or firewall rules.

CONTROL RELATIONSHIP:

- The kernel controls canonical identity, governance, firewall, IP, doctrine,
  registry and source-priority rules.
- This protocol controls the project research sequence, commercial analysis,
  management gate, client-safe extraction and conversion workflow.
- The decoded template controls exact layout, DOM, CSS, assets, geometry and
  print behavior for the named template role.
- The project record controls confirmed current scope and management-approved
  commercial decisions.
- No layer may silently override a higher-priority control or perform a function
  assigned to another layer.

03. STARTUP COMMAND AND REQUIRED FILE INSPECTION
======================================================================
Before researching, drafting or modifying any file:

1. Load and apply the attached GSSC production kernel.
2. Inspect every attachment before acting.
3. Read brand_assets and inventory the exact assets. Each asset is stored once,
   single-encoded, with its own decoded-image SHA-256. Verify every asset decodes
   and that its hash matches the declared value.
4. Decode the quotation payload and inspect its actual HTML, DOM, CSS, scripts,
   assets, page geometry, typography, page breaks and print rules. The stored
   payload is the TOKENIZED template: binary assets appear as {{GSSC_ASSET:name}}
   placeholders. Hydrate per Section 28C before rendering or delivering anything.
5. Identify the current client request and all project-specific supporting files.
6. Classify every input.
7. Confirm whether the task is research only, preliminary pricing, final
   conversion, revision, audit or client release.
8. Use the least-destructive source-preserving operation.

Do not begin the final quotation merely because a template and client name are
present. Complete the research, commercial, approval and firewall gates first.

If an essential source cannot be read or decoded, stop final conversion, state
the exact missing or unreadable input, and do not fabricate a replacement.

PACKAGE PREFLIGHT — REQUIRED PASS/FAIL REPORT:

RUN IT, DO NOT READ IT. The package carries an executable implementation of this
preflight in the runtime part. Extract and run it:

    python gssc_runtime.py preflight GSSC_Master_Package.json

It exits 0 on PASS and 1 on PRECHECK FAILED, and prints one line per check. The
prose below remains the governing specification; the runtime is its executable
form. If the two ever disagree, the prose governs and the runtime is the defect.
Manual execution of these checks remains acceptable where Python is unavailable.

- Confirm the master package is present, readable and valid JSON, and that all
  six top-level parts are present: manifest, kernel, execution_protocol,
  quotation_template_payload_base64, brand_assets and assembly.
- Validate the kernel object and report its internal kernel version.
- Confirm the kernel has exactly the module count declared in
  manifest.integrity.kernel_module_count, and exactly one changelog entry
  marked current.
- Validate quotation_template_payload_base64 as strict Base64 before decoding.
- Confirm the decoded TOKENIZED template begins with <!DOCTYPE html> and ends
  with </html>. Do NOT apply this markup test to brand_assets: those are binary
  image payloads and must instead decode to their declared MIME type with a
  matching sha256_of_decoded_image.
- Confirm every {{GSSC_ASSET:name}} token in the template resolves to an entry in
  brand_assets, and that no brand_assets entry is orphaned.
- Record the SHA-256 fingerprints declared in manifest.integrity in the project
  record, and recompute them using manifest.integrity.hash_method.
- Confirm the quotation source role: finished source-derived master, category
  master, geometry baseline, or universal template. Do not assume universality.
- If the template contains prior project content, treat it as source content to
  be replaced only in authorized variable regions; never carry prior client,
  pricing, date, specification or project facts into the new quotation.
- If any preflight check fails, label the package PRECHECK FAILED and do not
  proceed to client release.

05. RESEARCH STANDARD AND SOURCE DISCIPLINE
======================================================================
Research must be current, project-specific, geographically relevant and based on
comparable scope. Use official and primary sources first where available.
Cross-check material commercial conclusions using multiple independent sources
when practical.

For every factual or monetary research item, record:

- fact or amount
- currency
- tax basis: VAT-inclusive, VAT-exclusive, Non-VAT or unknown
- source title
- source publisher or provider
- source date or observation date
- geographic basis
- technical and scope basis
- whether delivery is included
- whether installation is included
- whether warranty is included
- retail, wholesale, distributor, contractor or turnkey classification
- verification status
- confidence: HIGH, MEDIUM or LOW
- limitations or comparability adjustments

Never combine values with different tax bases without first normalizing and
showing the arithmetic internally. Never present an unknown tax basis as known.
Do not fabricate citations, prices, quotations, statutes, wage orders, permits or
technical standards.

Research is evidence, not authority to overwrite a management-approved amount.
Once management selects the commercial position, do not silently change it.

16. DECISION ARCHITECTURE AND ETHICAL COMMERCIAL PERSUASION
======================================================================
Use only truthful, reviewable and non-coercive persuasion. Preserve the client's
ability to make an informed decision.

PERMITTED METHODS:

- anchor against a genuine and comparable market range
- establish scope and value before presenting price
- contrast genuine Essential, Recommended and Signature options
- identify one evidence-based recommended choice
- reduce unnecessary cognitive load
- show lifecycle or operational value when supported
- explain client coordination burden avoided
- clarify material inclusions and exclusions
- explain risk transferred to or managed by GSSC
- use specific, credible approved amounts
- present a clear acceptance and next-step path
- use validity periods tied to real source validity or volatility
- use warranty and accountability as truthful reassurance
- communicate urgency only when factually supported
- use calm, confident, precise and non-pressuring language

PROHIBITED METHODS:

- false scarcity
- fake deadlines
- fabricated competitor prices
- invented discounts or savings
- bait pricing
- hidden material exclusions
- emotional pressure or intimidation
- fear-based unsupported claims
- misleading comparisons
- presenting an optional upgrade as legally or technically mandatory
- exploiting a known client mistake
- concealing limitations or incompatibility
- knowingly quoting an unsuitable specification
- collusion
- misrepresenting related, coordinated or comparison quotations as independent
- language designed to prevent informed comparison

Review test:

Would the statement remain accurate and defensible if read together by the
client's procurement team, legal counsel, auditor and GSSC management?

If not, remove or rewrite it.

22A. DYNAMIC BODY DESIGN -- RESEARCH, TRANSLATE, MEMORY (GOVERNED BY KERNEL MODULE 15)
======================================================================
Apply this section for every body-region content decision, on every generation,

locked chrome (masthead, margins, footer, watermark, marginalia, signature
lockup), which remain governed by Sections 22 and 24 without exception.

TRIGGER -- ALWAYS ON:

Every body-content decision is freshly re-examined every time. There is no
complexity threshold and no exemption for content with an existing anatomy
(cards, tables). Re-examination may validly conclude that the existing pattern
is still correct -- freshness means the decision is genuinely re-made, not that
the output must differ from the last document produced.

DELEGATION TOPOLOGY:

- Operating inside the GSSC EXPIRA fleet: route the RESEARCH stage below to the
  Research specialist agent as a genuine subagent delegation.
- Operating as a licensed/derivative single-model deployment with no fleet
  available: perform all five stages serially within one reasoning pass. The
  doctrine is identical in both cases; only the execution topology differs.

FIVE-STAGE LOOP:

1. RESEARCH -- investigate the best way to present this specific content
   (chart-vs-table-vs-prose selection, arrangement, emphasis), citing the real
   precedent or pattern basis relied upon. Do not assert a design choice is
   best practice without a statable basis; this follows the same anti-
   fabrication discipline as Section 05.

2. TRANSLATE -- re-express whatever Stage 1 recommends using ONLY the existing
   GSSC token vocabulary (color palette, type scale, rule-weight grammar,
   spacing rhythm, opacity values already declared in the kernel's brand and
   quotation/document doctrine). This is a hard gate that never relaxes. A
   structurally new layout is permitted; a new color, font size, spacing value,
   or border weight outside the existing token set is not. If no existing
   token fits, stop and flag for a versioned kernel/brand update rather than
   inventing an ad hoc value silently.

3. INTEGRATE -- place the translated result inside the editable body region
   only, respecting the content-fit hierarchy in Section 23.

4. SELF-CHECK -- verify no clipping/overflow, no overlap, every color/size/
   spacing value traces to a declared token, locked chrome untouched, geometry
   unchanged. This is a construction-rule check, not a rendered-pixel check; it
   prevents defects by forcing token-only, geometry-preserving construction.

5. SELF-FIX -- on any Stage 4 failure, apply the Section 23 escalation order

   the failure stems from the Stage 1 choice itself being unworkable, cycle
   back to Stage 1 with a simpler ask rather than forcing a bad fit.

23A. LAYOUT BUDGET CALCULATOR -- COMPUTABLE OVERFLOW ESTIMATION (GOVERNED BY KERNEL MODULE 10 / 15)
======================================================================
HONESTY NOTE: this is a calibrated approximation, not a verified per-glyph
font-metrics engine and not a rendered screenshot. No headless browser or
HTML/CSS rendering engine (Chromium, Playwright, WeasyPrint, wkhtmltopdf) and
no working package installer (pip/npm) were found available in the operating
environment as of 6 August 2026 -- confirmed by direct search, not assumed.
This method reduces, but does not eliminate, the need for a literal rendered
check; if such a tool becomes available in a future environment, supersede
this method with literal rendered measurement per Module 16 non-regression
discipline.

GEOMETRY CONSTANTS (extracted directly from the quotation master's own CSS,
not assumed): page height 1123px; margin-top 96px; margin-bottom 120px; body
column width 540px (fixed, non-responsive); body padding by page -- Page 1
38/26px, Page 2 32/22px, Page 3 30/26px (top/bottom).

FONT SIZE AND LINE-HEIGHT REFERENCE (px): fs-body 10.5, fs-bodyL 11.5,
fs-title 42, fs-dek 13, fs-kicker 8, fs-caption 10, fs-section 9.
Line-height ratios: lh-body 1.58, lh-display 1.12, lh-lede 1.65, lh-tight 1.4.

ESTIMATION FORMULA:

1. Average character width = 0.50 x font-size-px. This is a commonly used
   design heuristic for proportional Latin body text, NOT independently
   verified against the actual Inter/Libre Baskerville font metrics tables
   (no internet-fetched font-metrics data available in this environment).
2. Characters per line = column-width-px / average-character-width-px.
3. Estimated lines = character-count / characters-per-line, rounded up.
4. Estimated block height = estimated-lines x (font-size-px x line-height
   ratio).
5. Available budget = (page-height - margin-top - margin-bottom) - page's
   body padding-top - body padding-bottom - height already used by prior
   elements on that page.
6. Safety margin = 0.85. Treat the block as fitting only if estimated block
   height is at or below 85% of the available budget, absorbing kerning,
   ligature, and hyphenation variance the flat character-width approximation
   does not capture. Above that threshold, treat it as AT-RISK and apply the
   Section 23 escalation hierarchy before finalizing.

VALIDATION ON RECORD (6 August 2026): calibrated and sanity-checked against
the master's own existing, presumed-working text blocks -- Page 1 lede
paragraph (301 characters, computed at 12.8% of remaining budget), Page 1 dek
paragraph (530 characters, 20.2%), Page 2 sig-desc block (286 characters,
5.8%) -- and against constructed forced-overflow scenarios, including a case
with 2,340 characters against only 100px of remaining budget, which correctly
computed as AT-RISK at 381.6% fill. Both the PASS and AT-RISK verdict
branches were confirmed to compute correctly from real arithmetic, not an
always-true default.

SCOPE LIMIT:

This method estimates TEXT BLOCK height only. It does not estimate or verify
image clipping, decorative-element overlap, CSS rendering defects, font-
loading failures, or any other non-text visual issue. Those remain governed
only by the qualitative construction-rule review already defined for Stage 4
self-check; treat this calculator as a genuine reduction in correction
iterations for text overflow specifically, not a complete substitute for
eventual visual/rendered confirmation.

23B. COLLISION AND BALANCE DETECTION (GOVERNED BY KERNEL MODULE 10 / 15)
======================================================================
Extends Section 23A's single-block vertical estimate to genuine 2D layout
risk: unintended overlap between simultaneously-visible elements (grid cells,
side-by-side content), visual imbalance between elements meant to read as
parallel or equal-weight, and horizontal overflow risk for fixed-width,
non-shrinking elements. Still not a rendered screenshot -- models element
geometry as axis-aligned bounding boxes from the template's own fixed CSS
constants (column counts, gaps, fixed widths).

AABB OVERLAP TEST:

Two boxes (x, y, width, height) overlap if and only if:
ax < bx+bw AND ax+aw > bx AND ay < by+bh AND ay+ah > by.
Verified 6 August 2026 against a deliberately overlapping pair (correctly
returned true) and a correctly-spaced 2-column pair (correctly returned
false) -- both branches confirmed, not a default.

GRID-ROW BALANCE CHECK:

For cells sharing a grid row, row height equals the maximum of that row's
cell heights (matching real CSS Grid auto-sizing behavior). Imbalance percent
= 100 x (max cell height - min cell height) / min cell height. Flag as
VISUALLY UNBALANCED above a 30% threshold -- an editorial-design heuristic
for when a reader would notice unequal weight between elements presented as
parallel choices, not an exact rendered measurement.

Validated 6 August 2026 against the REAL Page 2 research-grid content from
this session's own prior dynamic-body-design test output: correctly
identified a genuine 33.3% height imbalance between two grid cells that had
not been previously noticed without this check -- a concrete finding on real
content, not only a synthetic demonstration. Also confirmed against a
deliberately extreme forced case (699.4% imbalance), verifying the threshold
fires correctly at the extreme end too.

FIXED-WIDTH HORIZONTAL FIT CHECK:

For an element with a fixed width and a non-shrinking constraint (for
example flex-shrink:0), estimate whether given text fits on one line within
that width: characters per line = allotted width px / (0.50 x font-size px);
lines needed = ceiling(character count / characters per line). If the
surrounding CSS does not permit wrapping and more than one line is needed,
this is an overflow risk requiring attention before finalizing. Tested 6
August 2026 against the template's actual Page 3 bar-chart label constants
(150px width, 8px font-size): a 33-character label correctly estimated to
fit on one line; a 62-character label correctly estimated to require 2 lines.

USAGE:

These checks feed Stage 4 self-check as objective data. They inform, not
replace, the Stage 1 research decision on how to adjust a flagged layout --
see Section 22A's research stage, which explicitly includes spatial
alignment, relative sizing, and balance between simultaneously-visible
elements within its scope. Decide the best content-level or arrangement-level
fix using research judgment, then re-check with this section's calculations.

SCOPE LIMIT:

Currently models grid layouts and fixed-width flex children specifically --
the patterns present in the current template. A genuinely novel future
layout pattern not covered by these two models would need its own geometry
formula added at that time, per Section 22B's continuous-optimization
discipline.

28A. DELIVERY, FILE-SIZE AND DOWNLOAD ENGINEERING
======================================================================
A completed deliverable is not delivered until the recipient can actually open
it. Apply the following delivery discipline.

FILE-SIZE DISCIPLINE:
- Keep the self-contained HTML as small as brand and print quality allow.
- Embed each large Base64 asset ONCE. Where a masthead logo, seal, signature
  lockup or watermark repeats on every page, reference a single embedded copy
  through CSS (for example, content:url(...) on the element) instead of pasting
  the same payload into every page. In Chrome and Edge this renders byte-for-byte
  identical to a repeated src while dramatically reducing file size.
- This single-embed deduplication is lossless and preserves the print system. It
  is not a redesign and does not alter geometry, assets, watermark, footer or
  margins. Background graphics must remain ON for CSS-embedded assets to print.
- Oversized files can silently prevent the native download control from appearing
  on the recipient's client. A leaner file restores reliable delivery.

TRANSPORT COPY — OPTIONAL:
- Where a still-smaller copy helps transport, a near-lossless copy may be produced
  by quantizing only the flat brand raster assets (watermark, logos, seal,
  signature) to a reduced palette. Keep the full-fidelity file as the
  authoritative deliverable and label the reduced file clearly as a web/transport
  copy. Never quantize away legibility or brand fidelity on the authoritative file.

DELIVERY CHANNELS, IN ORDER OF PREFERENCE:
1. Native self-contained HTML download control for the on-disk file.
2. Plain, resolvable file links (for example, the user's OneDrive) presented as
   plain text. Plain links render even when a recipient's client is intermittently
   blocking cards, buttons or download chips.
3. A simple link hub only when its links point to fully resolvable absolute URLs.

DELIVERY RULES:
- Prefer plain-text links as the resilient fallback whenever a recipient reports
  that buttons, cards or download chips are not rendering.
- Do not attempt to move binary or image-bearing files through chat text; binary
  content cannot be reproduced faithfully in a message. Route such files through a
  file channel (download control or file storage), never through transcription.
- Confirm with the recipient that the delivered link or control actually opened
  before treating the task as delivered.

normally-sized delivery. This section governs the DIFFERENT condition where the
DELIVERY MECHANISM ITSELF is unavailable -- a file-upload tool, document-library
write, or direct file-send call errors, including on a trivial test file, such
that no file channel (native download, file-storage push, or link) can succeed
regardless of size or recipient client capability.

DISTINGUISHING THE TWO CONDITIONS:

- Recipient-rendering failure (Section 28A): the delivery call succeeds, but the
  recipient reports the file, button, card, or chip did not display or open.
- Channel failure (this section): the delivery call itself returns an error,
  including on a minimal probe file, indicating the transport layer -- not the
  recipient -- is the point of failure.

Confirm which condition applies with a minimal test before choosing a remedy:
if a trivial one-line file also fails to send or upload, treat it as a channel
failure and apply this section rather than retrying Section 28A's channel list
indefinitely.

INLINE VERIFICATION RENDER -- PROCEDURE:

1. Identify every large embedded binary payload in the deliverable (base64 image
   data URIs, embedded fonts, or other non-text blobs) that is not itself the
   subject of the current request.
2. Replace each such payload with a short, explicitly labeled placeholder string
   naming what was removed and stating it is byte-identical in the full-fidelity
   file (for example: "[TRIMMED FOR CHAT DELIVERY -- watermark image, byte-
   identical in the full package/file saved server-side]"). Never remove or
   alter surrounding structure, CSS rules, DOM, or text content -- only the
   binary payload itself is substituted.
3. Confirm the resulting file is materially smaller and consists entirely of
   plain text (HTML markup, CSS rules using var()-based tokens, JSON, or other
   inherently textual content) suitable for direct inline transmission.
4. Paste the complete resulting source inline in the chat response itself as
   the deliverable, exactly once, in full -- not truncated or summarized.
5. State plainly, in the same response, which specific elements were
   placeholder-substituted, and that the unmodified, full-fidelity original
   (with every real binary payload intact) remains saved and available through
   the normal file channel once it recovers.
6. This procedure does not alter, approximate, or lossily compress any text,
   markup, CSS, or structural content. Only non-text binary payloads unrelated
   to the current task are substituted, and only with explicit disclosure. It
   is a controlled, narrow exception to the Section 28A rule against moving
   binary content through chat text -- it never transcribes binary data itself,
   it substitutes a disclosed placeholder for it.

WHEN TO APPLY:

Apply this section proactively the moment any file-delivery tool call errors,
rather than waiting for the recipient to report a problem or retrying the same
failing channel repeatedly. Different chat interfaces and API-connected models
vary in file-upload size limits, binary-handling capability, and whether file
delivery is supported at all -- this section is the universal fallback that
functions inside any text-capable interface regardless of that variance.

RECOVERY:

Once the normal file channel is confirmed working again (for example, a later
trivial probe file succeeds), resume standard Section 28A delivery for the
full-fidelity file and note the successful handoff. The inline verification
render is a stopgap for continuity and review, not a permanent replacement for
the authoritative full-fidelity deliverable.

FAILURE CONDITIONS SPECIFIC TO THIS SECTION:

- Treating a channel failure as if it were a recipient-rendering problem, and
  retrying Section 28A's channel list indefinitely without ever falling back.
- Silently altering text, markup, CSS values, or structure while trimming --
  only binary payloads may be substituted, and only with disclosure.
- Failing to disclose which elements were placeholder-substituted.
- Failing to note that the full-fidelity original remains available once the
  channel recovers.
- Attempting to transcribe actual binary data into chat text instead of using
  a disclosed placeholder.

28C. ASSET HYDRATION AND ASSEMBLY (GOVERNED BY KERNEL MODULE 03 / 05 / 10)
======================================================================
The stored quotation payload is the TOKENIZED template. Every binary brand asset
is held exactly once in brand_assets and referenced from the template by an
opaque placeholder of the form {{GSSC_ASSET:name}}.

WHY THIS EXISTS:
Section 28A already requires single-embed Base64 asset deduplication. Storing an
asset both in the asset repository and again inside the template violated that
rule and inflated the shipped package, because template bytes are Base64-encoded
a second time on the way into the container. Tokenizing removes the duplication
without altering one character of text, markup, geometry or typography.

HYDRATION IS MANDATORY BEFORE DELIVERY:
The tokenized template is a STORAGE form, not a deliverable. It must never be
sent to a client, opened as a finished document, or treated as the rendered
quotation. Hydrate first.

PROCEDURE (executable form: python gssc_runtime.py hydrate <package> -o out.html):
1. Decode quotation_template_payload_base64 to UTF-8 text.
2. For each token {{GSSC_ASSET:name}}, look up brand_assets[name].
3. Replace the token with: data:<mime>;base64,<base64>
   using the entry's own mime and base64 values, verbatim.
4. Replace tokens ONLY. Never edit surrounding markup during hydration.
5. Verify each decoded asset against its sha256_of_decoded_image before use.
6. The hydrated result must equal assembly.verification.hydrated_template_sha256.
   If it does not, stop: the package is damaged or has been altered. Do not
   deliver, and do not attempt a partial repair.

FAILURE CONDITIONS:
- An unresolved token remains in a client-facing file. HARD STOP.
- An asset hash does not match its declared value. HARD STOP.
- A brand_assets entry is orphaned (declared but never referenced). Report it;
  it indicates the template and the asset repository have diverged.
- The hydrated hash does not match the declared verification value. HARD STOP.

STANDALONE RENDERING:
A hydrated file is fully self-contained and renders offline with no external
request, exactly as before. This preserves the single-file offline portability
principle. The saving is in transport and storage, never in the delivered
artifact.

23C. FOOTER AND GEOMETRIC OVERLAP -- CUMULATIVE CURSOR (GOVERNED BY KERNEL MODULE 10 / 17)
======================================================================
HONESTY NOTE: this shares Section 23A's calibrated approximation and none of
its certainty. It is not a rendered screenshot. What changes is not the
accuracy of the estimate but its RESOLUTION: 23A answers whether a page is too
full on aggregate; it cannot answer which block crosses the footer, or by how
many pixels. Those are the two facts an operator needs before applying the
Section 23 escalation ladder, and neither was obtainable before this section.

METHOD:

Walk the FLOWED body blocks of each page in document order. Maintain a running
Y cursor beginning at margin-top plus that page's own body padding-top. After
each block, test its own bottom edge against two boundaries, both derived from
geometry already declared in Module 10, not invented here:

  SOFT  page-height - margin-bottom - body padding-bottom. The block has
        entered the page's own reserve. Still inside the margin, but the
        buffer is gone.
  HARD  page-height - margin-bottom. The block has entered the footer band
        itself -- running footer, seal, folio and contact anchor.

On the universal master these resolve to a hard line at 1003px (1123 - 120) and
a soft line at 977px or 981px depending on the page's own bottom padding.

Absolutely-positioned locked chrome -- masthead, colophon, margin rail,
watermark -- is EXCLUDED from the cursor. It does not participate in flow, and
including it causes the walk to mis-attribute an overflow to a footer element
that never flowed. The first prototype of this section did exactly that,
naming .footer-secondary as the offending block on a forced fixture whose real
cause was an injected paragraph several elements earlier.

Figure heights, table cell type sizes and the declared block separation share
the SAME cursor rather than being measured separately, so the walk is not a
prose-only estimate.

VALIDATION ON RECORD (21 September 2026): executed against the real hydrated 2.10.0
derivative and against a deliberately forced-overflow fixture. Real derivative:
5 pages, all PASS, smallest headroom 215px on page 5.
Forced fixture: correctly FAILED, naming the offending block and its overflow
in pixels. Both branches confirmed to compute from real arithmetic, not a
default.

SCOPE LIMIT:

Raster image heights, CSS rendering defects and webfont-loading failure remain
outside this check, as they remain outside every other check in this package.
The header-boundary and marginalia-boundary variants of the same cursor are a
direct extension of this method and are NOT yet built.

35. PAGE ARCHETYPE CREATIVITY ENGINE (GOVERNED BY KERNEL MODULE 18)
======================================================================
Creative latitude is resolved REGION BY REGION, not page by page, and is
expressed as a budget from 0 to 3.

  0  Verbatim. Module 15 Stage 1 is skipped entirely. Deviation is a hard stop
     of the same tier as Sections 21 and 24.
  1  Token-constrained micro-variation within already-approved states.

independently and THE LOWEST BUDGET IN PLAY GOVERNS any decision spanning them.

III commercial body, which is fully researchable, and the canonical signoff

36. CONTRAST AUDIT (GOVERNED BY KERNEL MODULE 03)
======================================================================
Every declared foreground/background pairing is measured by WCAG 2.x relative
luminance against a declared small-text floor of 4.5:1.

Print is not bound by WCAG. The luminance physics are identical on paper: a
pairing below the floor at small size reads faint under office lighting too.

A pairing may sit below the floor ONLY with an explicit exempt_reason recorded
in 03_brand.document_type_system.contrast_registry. An exemption is a decision
on the record, never a silence. Two exist at 2.11.0, both for the gold ordinal
in the header and the contents row, both on the same ground: the ordinal is a
redundant navigational marker whose value also appears in the contents page and
the margin rail, so no information is lost if it reads softly, and the gold
jewel against the navy title is the intended restraint of the register.

38. COVER OVERTURE (GOVERNED BY KERNEL MODULE 18)
======================================================================
The cover is the only archetype carrying creativity budget 3, and budget 3
requires a live precedent check before Stage 2 translation.

Through 2.10.0 that check had never been performed for the universal master and
the latitude had never been used: page 1 was a stacked text sequence
structurally indistinguishable from a budget-2 prose page.

The treatment adopted is scale dissonance with strict isolation. Exactly ONE
element is raised -- the cover title, from --fs-title to --fs-dropcap, both

effect holds only while the isolated element remains the exception.

Photography is NOT the instrument. 03_brand.photography.default is "avoid when
possible"; a cover overture is compositional and typographic.

A cover overture may not add, remove or reword content. It is a restyle.

23D. RESOLVED BOX MODEL -- BINDING OVERFLOW GATE (GOVERNED BY KERNEL MODULE 10)
======================================================================
Sections 23A and 23C are retained as fast coarse passes. Section 23D decides.

WHY THIS SECTION EXISTS:

A human caught a footer overlap on page 1 of the 2.11.0 master by eye, on a
page that Section 23C had reported PASS with 205px of headroom. The page
overflowed its footer band by 216px. That is a 421px error, and it ran in the
direction that hides defects rather than inventing them. The check that exists
to catch overlap shipped an overlap.

The cause was not arithmetic. Sections 23A and 23C costed a block as text
height alone, from a hardcoded class-to-size map, and were therefore blind to
four things the browser is not:

  1. ELEMENT MARGIN AND PADDING, never added at all. Page 1 carries 114px of
     margin and 36px of padding and borders: 150px, roughly 18% of the usable
     page, entirely outside the estimate.
  2. max-width. The estimate always wrapped at the 540px body column. The
     2.11.0 cover title was max-width:470px -- four lines at 540px, SIX at
     470px, a 143px error on one element.
  3. LATE CASCADE OVERRIDES. A hardcoded map cannot see a property redeclared
     in a later style block or scoped to a page.
  4. MARGIN COLLAPSING. Adjacent sibling margins collapse to the larger of the
     two; naive summation over-counts.

METHOD:

Parse the document's own style blocks. Resolve :root custom properties. Apply
the real cascade by specificity then source order. Compute content height from
a max-width-aware greedy wrap, add padding and borders, and collapse sibling
margins. Wrapper elements that only nest other measured elements are skipped by
name so nothing is counted twice.

Custom property names are CASE-SENSITIVE. This stylesheet uses camelCase
(--fs-bodyL), and a lowercase-only pattern silently resolves to None and falls
back to a default. That defect was found and fixed during this build.

SCOPE LIMIT:

Not a rendered screenshot. Floats, flex and grid track sizing are not modelled,
and the dropcap shape is not modelled. It closes the four blindnesses named
above, which is what produced this defect. Browser print-to-PDF at A4 remains
the only visual confirmation.

Executable: gssc_runtime.py boxcheck <package.json> --file <built.html>

38A. THE PAGE BUDGET GATE (GOVERNED BY KERNEL MODULE 18)
======================================================================
No archetype treatment, at any creativity budget, may push a page past its
content budget. The page budget outranks every creative latitude in Module 18,
including budget 3.

Section 23D must PASS on the built derivative before a treatment is adopted. A
treatment that fails is REVERTED, not rationalised and not shipped with a
caveat.

This gate exists because the 2.11.0 cover overture was reasoned from genuine
editorial precedent, was internally coherent, passed every check the package
had, and was still wrong -- because nothing connected the creative decision to
the page it had to live on.

A cover overture may not add, remove or reword content. Where a page has no
room for an overture, the correct finding is that the page must be shortened
editorially first. That is a content decision for management, not a design

23E. COVERAGE LEDGER -- NO SILENT OMISSION (GOVERNED BY KERNEL MODULE 10)
======================================================================
Four incidents in this package's history share one root cause, and it is not
arithmetic.

  2.11.0  page 1 overflowed its footer by 216px while the checker reported
          PASS with 205px of headroom.
  2.12.0  the categorical header's stamp line contributed real height that
          nothing measured.
  2.12.0  every table rule failed its ancestor test, so no table styling
          resolved at all.
  2.12.0  the regex scan resumed after each match, so elements nested inside
          an already-matched parent were NEVER VISITED -- .chs-stamp,
          .sig-code, .sig-name and .sig-desc were all invisible to the model
          while being visible on the page.

In every case the model met something it did not understand and QUIETLY
CONTINUED, producing a confident number wrong in the direction that hides
defects. Patching each instance does not prevent the next one.

Two structural changes make silence impossible:

  A REAL DOM WALK replaces the regex scan. Every element is visited exactly
  once, at its true depth, with true sibling positions -- which also makes
  structural pseudo-classes evaluable instead of silently dropped.

  A COVERAGE LEDGER records every element as MEASURED, EXCLUDED by a named
  declared rule, or UNACCOUNTED. Section 23D FAILS on any unaccounted element.
  A future component built from a construct this model does not handle becomes
  a loud, named failure rather than a silent zero.

A selector this resolver cannot evaluate is likewise recorded and EXCLUDED,
never assumed to match.

39. DATA SERIES COLOUR (GOVERNED BY KERNEL MODULE 03)
======================================================================
Colour in a chart encodes information. It is not brand decoration and it does
not follow brand-accent rules.

THREE PALETTE TYPES, matched to the shape of the data:
  CATEGORICAL  unordered groups. Hues must differ in BOTH hue and lightness.
  SEQUENTIAL   one ordered quantity. A single hue ramped light to dark, which
               must read as correctly ordered when desaturated.
  DIVERGING    a meaningful centre. Two hues meeting at a neutral middle.

THE GRAYSCALE TEST IS BINDING. Adjacent categorical series must differ by at
least 0.04 relative luminance. This is not a preference: hue alone collapses in
grayscale, in low-quality print, and under the red-green deficiency carried by
roughly 8% of men. The 2.12.0 palette failed this test -- mid_grey sat 0.038
from gold_deep -- which is why a fifth series could not be added without a new
token.

COLOUR IS NEVER THE ONLY CHANNEL. Every series declares a pattern and prints
its value as a text label.

CAP AT FIVE CATEGORICAL SERIES. Past that, split the chart rather than adding
hues; a sixth series cannot be given a luminance slot both distinct from its
neighbours and inside the brand.

A new colour token is added to the master through a kernel version, with its
measurement on the record. It is never invented inside a derivative.

======================================================================
43. FORWARD-COMPATIBILITY GUARD (GOVERNED BY KERNEL MODULES 03 AND 10)
======================================================================
Every defect this package has shipped had one shape: a construct the model did
not know about, met silently, and costed as zero or as a default. The coverage
ledger (Section 23E) closed that for element HEIGHT. This section closes it for
the REGISTRIES -- the declared tables a future design iteration will extend, and
that nothing previously forced it to extend completely.

It is deliberately a set of REGISTRY COMPLETENESS tests. Each names something a
future iteration is likely to add, and fails if that thing is added to one place
and not the other:

  1. Every palette colour is contrast-registered as text, or listed as non-text.
     Adding a colour forces "is this ever text, and at what size" to be answered
     when the token is added, not discovered in a printed proof.
  2. Every chart series pattern comes from the declared pattern vocabulary, and
     spare names are declared ahead of need so a sixth series has somewhere to
     go that is already specified.
  3. Supported layout modes are declared, and no stylesheet may use a mode
     outside them. A new layout primitive forces a deliberate decision --
     implement it or declare the gap -- instead of silent mis-measurement.
  4. NO IN-FLOW GENERATED CONTENT. A ::before or ::after that is not absolutely
     positioned and not display:none injects text that never appears in the
     parsed HTML and is therefore invisible to any DOM box model. This is
     forbidden rather than modelled.
  5. Every signature block is governance-checked, not merely the first.
  6. No registered flex-row or container class is stale, so a registry entry
     that no longer matches the document is visible rather than quietly inert.

THE PRINCIPLE: a registry that can be extended incompletely will eventually be
extended incompletely. Complexity is welcome where it buys a guarantee; what is
not welcome is a declared table that nobody is forced to keep whole.

Executable: gssc_runtime.py futureproof <package.json> --file <built.html>
